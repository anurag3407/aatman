# Internationalisation

## Scope

Aatman supports English (`en`) and Hindi (`hi`). Every user-visible string — questions,
options, headings, templates, errors, crisis copy, staff labels — lives in a catalog. There is
no runtime translation service and no third-party i18n library.

Sources: `src/messages/en.ts`, `src/messages/hi.ts`, `src/lib/i18n/`.

## Locale resolution

Server-side (`getLocale()`):

1. `aat_lang` cookie, if it is `en` or `hi`.
2. `Accept-Language` header, if it begins with `hi` (case-insensitive, optional whitespace).
3. English.

There is no geolocation and no per-user stored preference. The cookie is set by the language
toggle (1 year, SameSite=Lax, JS-readable by design).

Client-side: the server passes only the resolved locale into `I18nProvider`; both catalogs are
bundled, so `useI18n()` is synchronous.

```tsx
// server
const { locale, m } = await getMessages();
<I18nProvider locale={locale}>…</I18nProvider>

// client
const { m, locale } = useI18n();
```

## Catalog shape

`en.ts` exports a `Messages` object with nested sections:

| Section | Contents |
|---|---|
| `common` | App name, navigation, generic actions, disclaimers |
| `companion` | Companion voice lines |
| `home` | Landing page |
| `consent` | Age gate and consent points |
| `signin` | Provider buttons, dev login, error keys |
| `checkin` | Intro, progress, Likert labels, PHQ/GAD items, C-SSRS questions, campus questions, deeper offer, free text, submit |
| `results` | Tier headings, summary labels, crisis actions, next steps, tips, score details, banners |
| `templates` | Five clinician-written tier notes |
| `book` | Booking copy and errors |
| `history` | Chart and retention copy |
| `settings` | Export/erase |
| `exercises` | Breathing, grounding, sleep tips, thought record |
| `chat` | Intro, notices, pause copy, fallback, limit |
| `privacy` | Privacy notice sections |
| `signin.errors` | Error messages keyed by auth failure reason |

`hi.ts` must mirror the structure exactly, including array lengths.

The `Messages` type is inferred from `en.ts`, so TypeScript catches missing fields at build
time. Runtime structure checks catch array-length and placeholder drift.

## Formatting

```ts
fmt(template, vars)         // replaces {name} placeholders
intlLocale(locale)          // "en-IN" | "hi-IN"
TIME_ZONE = "Asia/Kolkata"
formatDate(value, locale, opts)
```

All dates are formatted in IST so server and browser render identical text. Examples:

- Booking lists: `Mon, 3 Nov, 6:30 pm` (English) / Hindi month names via `hi-IN`.
- Results timestamp: medium date + short time.
- Alerts: medium date + short time + "IST".
- History chart endpoints: day + short month.
- SMS reminders: English, IST, neutral wording.

Numeric formatting uses `toLocaleString("en-IN")` in admin views.

## Language toggle

`LanguageToggle`:

1. Computes the next locale.
2. Writes `aat_lang` via `document.cookie` with `max-age=31536000`, `samesite=lax`.
3. Calls `router.refresh()` so server components re-render.

The button label shows the **next** language (e.g. "हिंदी" when in English), with an accessible
label in the current UI.

The crisis page deliberately ignores the toggle: it shows English and Hindi together, because
someone in crisis should not have to find a language switch.

## Clinical content rules

| Rule | Rationale |
|---|---|
| Question wording is clinical content | Changes require clinical lead review |
| Band labels are not diagnoses | Student copy maps codes to neutral descriptions |
| Hindi PHQ/GAD items must be validated translations | The current Hindi items are a **draft** and must be replaced with official validated versions (phqscreeners.com) |
| Hindi clinical copy needs a Hindi-speaking clinician review | Idiom and tone affect disclosure |
| Templates are clinician-written | Not machine-translated |
| Crisis copy is bilingual and explicit | No ambiguity about emergency numbers |

Launch checklist items C4 and C5 cover validated instruments and copy approval.

## Testing

`tests/i18n/messages.test.ts`:

| Test | What it guards |
|---|---|
| Structure matches English, including list lengths | No missing/extra keys or arrays |
| Every questionnaire item exists | 9 PHQ + 7 GAD + C-SSRS + campus |
| Clinical content uses Devanagari | Hindi is not left in Latin script |
| Placeholders are preserved | `{done}`, `{total}`, `{months}`, `{when}`, `{n}` match |

The e2e suite also checks that the language switch translates the app and the check-in.

### What the tests do not catch

- Translation quality, tone, or clinical equivalence.
- Layout overflow for long Hindi strings.
- Font rendering on unusual devices.
- Right-to-left languages (not supported).

These need human review and visual QA in both locales.

## Placeholders

Supported pattern: `{key}` with word characters. `fmt` leaves unknown placeholders untouched
rather than replacing with `undefined`.

Examples:

```ts
fmt(m.checkin.progress, { done, total })        // "{done} of {total}"
fmt(m.history.retention, { months })            // retention window
fmt(m.book.chooseNewTime, { when })             // reschedule banner
fmt(m.exercises.breathing.rounds, { n: round })
```

The structure test compares placeholder sets per string.

## Fonts and typography

The root layout loads:

- Geist (Latin sans) + Noto Sans Devanagari
- Fraunces (Latin display serif) + Noto Serif Devanagari
- Geist Mono, Unbounded

CSS variables compose them:

```css
--font-sans: var(--font-geist-sans), var(--font-devanagari), system-ui, sans-serif;
--font-serif: var(--font-fraunces), var(--font-serif-devanagari), Georgia, serif;
```

Devanagari falls back to Noto when the Latin font lacks glyphs. Headings using the serif stack
render Devanagari with Noto Serif Devanagari.

Inline Hindi on the crisis page uses `lang="hi"` so screen readers and fonts handle it
correctly. The student shell sets `lang={locale}` on the wrapper.

## Adding or changing copy

1. Add the key to `en.ts` first; TypeScript will flag `hi.ts`.
2. Add the Hindi translation with the same placeholders and array lengths.
3. If the copy is clinical (questions, templates, crisis), route it through clinical review.
4. If it changes consent materially, bump `CONSENT_VERSION`.
5. Run `pnpm test tests/i18n`.
6. Visually check both locales on a narrow viewport.

### Adding a third language

The current design assumes two catalogs and a binary toggle. Adding a language requires:

- a new catalog file and `Locale` union member,
- a `messagesFor` branch,
- a toggle that cycles rather than flips,
- font coverage,
- `Accept-Language` parsing,
- clinical validation of instruments,
- updates to tests that assume `en`/`hi`.

This is a product and clinical decision, not a mechanical change.

## Known limitations

| Limitation | Effect |
|---|---|
| Both catalogs ship to the client | Bundle size grows linearly with languages |
| Binary toggle | Not suitable for 3+ languages without a redesign |
| Draft Hindi instruments | Not clinically valid until replaced |
| Hinglish | Supported in chat (model replies in kind), not in UI copy |
| No pluralisation engine | Strings use explicit wording or numeric placeholders |
| No RTL | Not supported |
| IST-only | Correct for the campus; not portable to other time zones without change |
